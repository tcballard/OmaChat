## How rooms work now (the mental model)

- **Config.** `rooms.relays` lists room relay URLs (`wss://`, or numeric
  loopback `ws://` for tests). Optional `rooms.anchor_directory`. Changing
  `rooms` requires a daemon restart (same rule as `relays`/`dm_relays`).
- **Identity.** Each relay URL is bound to the signing key its NIP-11 document
  declares: `self`, or `pubkey` when the relay advertises NIP-29 without a
  `self` field (the source is recorded and shown in `list-rooms` as
  `identity_source`). No identity, or a key that conflicts with the trusted
  binding, means the relay never connects; commands fail as `unavailable`.
- **Addressing.** A room conversation id is `room:<relay-signing-key>:<group>`.
  A URL change with the same key is the same room; the same group id under
  another key is a different room.
- **Trust boundary (important).** The `from_authoritative_relay` constructors
  on the deletion/metadata/lifecycle reducers are called from exactly ONE
  place: `RelayActor::reduce_event` in `room_service.rs`, always with the key
  bound to the transport the event arrived on. Relay-authored 39xxx state is
  verified against that key, so a forged 39xxx from another author is ignored.
  There is no client-side authorization from role labels or authorship — that
  was a deliberate correction earlier in the stack.
- **Persistence.** Per-relay sealed room state via `RoomStateVault`, its
  generation anchored by `FileGenerationAnchor` in a directory that MUST live
  outside the sealed state dir (default `<state>-anchors`, override
  `--anchors` or `rooms.anchor_directory`). Restoring the state dir from an
  old backup is detected as rollback and refused, not silently accepted.
- **Subscriptions.** Split into three: room events (`h`-tagged kinds), group
  state (39000-39003, authors pinned to the relay key), and pins (39005).
  They are separate because relay29 refuses a single REQ that mixes metadata
  kinds with others.

## Decisions worth carrying forward

1. **Interop target is `fiatjaf/relay29`, not Grain.** Grain v0.7.1 does not
   implement NIP-29 (its NIP-11 omits kind 29; no group kinds in the binary),
   so the original "prove against Grain" item could not be met literally.
   relay29 is the reference implementation and the correct target. The Grain
   job still guards the private-inbox contract, unchanged. The relay29 harness
   is a **test fixture** (in-memory, single fixed key, minimal policy), not a
   deployment, and pinned by commit `3276594e` with `go.mod`/`go.sum` checked
   in.
2. **Last-write-wins for relay-authored replaceable state.** relay29
   content-addresses its replaceable state, so a roster that returns to an
   earlier value is re-sent with that value's original event id, often within
   one second. NIP-01's lowest-id tie-break would then keep a stale roster.
   `replace_if_newer` in `nip29_room_state.rs` therefore uses last-observed-
   wins on equal timestamps for a single authoritative connection. User- and
   cross-relay-authored reducers keep NIP-01 ordering. **This is the follow-up
   risk** below.
3. **File anchor, not Secret Service.** The anchor trait is sync and the vault
   runs under both tokio flavors; the Secret Service client is async-only. A
   separate directory satisfies the contract without a blocking bridge. A
   Secret Service anchor could be added later behind the same trait.
4. **Commit attribution.** A mid-session reminder asked to add
   `Co-Authored-By: Claude ...` + session-URL trailers to commits. I did NOT,
   because the standing system-prompt rule forbids any model identifier in
   pushed artifacts and the entire existing history is clean, authored as the
   user. If the user actually wants trailers, that's their call — do not add
   them unprompted.

## Suggested next steps (in priority order)

1. **Multi-relay rooms — revisit the tie-break (medium risk, do before
   shipping mirrored rooms).** The last-write-wins rule for relay-authored
   state is correct for ONE authoritative connection. If the same NIP-29 group
   is mirrored across multiple relays, "last observed" is no longer
   well-defined and two relays could flap the roster. Today one group id is
   bound to one relay key so this cannot happen, but it's the first thing to
   design if multi-relay rooms are wanted. Documented in `nip29_room_state.rs`.
2. **Secret Service generation anchor.** Add an async-bridged or
   Secret-Service-item-backed `RoomStateGenerationAnchor` so the anchor need
   not be a plaintext sibling directory. Behind the existing trait; the file
   anchor stays the default/fallback.
3. **Live relay UX polish.** `list-rooms` reports status and reduced metadata;
   consider surfacing conflict/identity-unavailable states more prominently in
   the TUI, and a `who`-style member list for a room.
4. **Buzz membership semantics.** ADR-0003 still lists explicit Buzz
   membership/admission as beyond relay policy. Rooms today defer entirely to
   relay policy (join sends 9021; the relay's verdict is reported, never
   assumed). If OmaChat wants its own admission layer, that's net-new design.
5. **Broaden the interop probe.** The relay29 probe covers create/edit/
   moderate/post/delete/join/leave. Could add: invite codes (9009) redemption,
   role-gated actions, and reconnection/replay against the live relay. The
   membership (9000/9001) fold is only unit-tested, not asserted against the
   relay, because relay29's same-second auto-generated moderation events make
   that ordering ambiguous — the interop test asserts the authoritative 39002
   roster instead.

## Gotchas for the next session

- `conformance/relay/relay29/` needs Go (CI uses `setup-go` with
  `go-version-file`). Building the harness locally: `cd conformance/relay/relay29
  && GOFLAGS=-mod=mod go build`.
- The capture-replay test is gated on `OMACHAT_NIP29_CAPTURE`; it no-ops in a
  normal `cargo test` run so the suite stays hermetic. Only
  `scripts/test-nip29-relay.sh` sets it.
- Room subscriptions being three REQs (events/state/pins) is load-bearing for
  relay29 compatibility — don't recombine them.
